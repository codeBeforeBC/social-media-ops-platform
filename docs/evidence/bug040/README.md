# BUG-040 删除被拒绝但用户看不到反馈

2026-10-29；Codex；工作目录 `/Users/junlong/projects/social-mdeida-ops-platform`，分支 `codex/s9-acceptance`，`ad4edd7` 加CHANGE-023/024及本轮未提交修改。状态仅维护于[开发进度](../../tracking/开发进度.md)。使用investigate流程先取证、复现，再最小修复。

## 原因与证据

API现有日志显示用户两次DELETE已到达服务，分别64ms/21ms返回409。对相同目标的只读检查发现1条AI生成记录、6个选题、1条任务历史、1条事件历史，因此按原规则该账号不能物理删除。

页面把删除异常写到详情抽屉顶部的通用ErrorState，确认按钮在下方。点击时抽屉已滚动，错误位于屏幕外。[实际页面复现](diagnosis.json)中，错误框y=-205，确认区内没有错误；[修复前截图](screenshots/before-1440.png)。DELETE在复现中被拦截为按实际关联数据构造的409，未真实重试删除，不把拦截响应冒充抓到的原响应正文。

另一个已复现路径：隐藏的核验区仍会轮询，父级通用刷新无条件清空failure，导致删除拒绝提示又被清掉。[第一项回归先失败](browser-red.log)、[后台刷新回归先失败](poll-error-red.log)均保留，未凭猜测调整服务端保护。

## 修复

[账号页面](../../../apps/web/src/main.tsx)仅在删除确认区域显示删除错误，自动聚焦并滚动进入视野；同一错误不在顶部重复显示。后台核验刷新在删除模式下保留拒绝提示，直到用户重试、取消或明确读取最新账号。未修改删除权限、关联检查、数据清理或审计规则。
