# 小红书导航问题验证

日期：2026-10-07（Asia/Shanghai）。关联 BUG-001、S0-02/03、NAV-01–03。档案：用户指定的“yoyo运营”/`zrcmcu2d`。实际 Chrome 154.0.8037.99、OpenCLI 1.8.8、Bridge 1.0.24。

结论：**同样的 Navigation rejected 在中性网站复现，故障发生在浏览器 Bridge 导航阶段；已验证保留 debugger 连接的兼容读取路径，累计11次导航全部成功。** 原生CLI命令也各成功了一次，但间歇性故障不能据此称为已修复。全新安装的完整读取矩阵仍暴露类型筛选/识别不一致，登记 BUG-002，不能将导航成功等同于来源完整验收。

后续更新（2026-10-07）：本文保留前轮诊断与失败记录。[媒体类型识别修复报告](小红书媒体类型识别修复.md)已确认BUG-002是Live Photo误识别并修复，原完整矩阵及同一失败样本复验通过。下文“当前待定位/复验失败”描述均为本报告当轮观察；最新状态见台账。

## 已定位的层级和仍有的不确定性

本轮开始 doctor 显示扩展未连接；重启本地 daemon 后 `zrcmcu2d` 自动连接，doctor 正常，没有切换档案或重新登录。随后原生“情绪价值”搜索返回3条；使用当前搜索结果中的签名链接，原生note读取返回7个字段。

在同一profile使用OpenCLI Page对象的 adapter surface 访问 `https://example.com`，第一次导航在347ms返回 `Navigation rejected.`。紧接着读取页面，却已看到 Example Domain；第二次普通导航成功。这证明该错误并非小红书关键词或登录所独有，也提示拒绝响应不能简单解释为“导航肯定没发生”。本项目没有添加盲目重试。

扩展1.0.24的 `handleNavigate` 在没有活跃network capture时先执行 `detach(tabId)`，随后调用 `chrome.tabs.update`；租约创建还可能先用目标URL初始化标签页。CLI Page.goto转发该错误。现有源码和上游实测支持debugger解除/标签页导航时序的兼容性假设，但本轮没有插装Chrome内部或修改扩展，**尚未单独证明detach时序是唯一根因**。

上游有相同直接观察：[导航前detach与拒绝报告 #2487](https://github.com/jackwener/OpenCLI/issues/2487)、[小红书note报告 #2515](https://github.com/jackwener/OpenCLI/issues/2515)、[间歇性adapter导航报告 #2533](https://github.com/jackwener/OpenCLI/issues/2533)。这些报告用于提出并核对假设；本项目结论以本机证据为准，不把上游临时修复当作已发布修复。

## 可复现脚本

- [prepare-opencli-xhs.mjs](../../../tools/s0/prepare-opencli-xhs.mjs)：要求OpenCLI1.8.8和原文件SHA-256精确匹配，应用已验证的可见性修正；依赖变化拒绝写入，已经修正的文件可重复使用。
- [probe-xhs-navigation.mjs](../../../tools/s0/probe-xhs-navigation.mjs)：显式profile，保留debugger、非HTTP capture模式；每个关键词最多3条、每轮3篇详情；详情按目标ID和字段稳定条件等待，最长12秒，不对导航/登录/安全拒绝自动重试。失败即停止，关闭本轮租约。
- [受控测试](../../../tools/s0/probe-xhs-navigation.test.mjs)：8项通过，覆盖签名脱敏/错误URL、null与0及近似互动、错笔记ID、登录/安全/不可访问、未加载/缺面板、原文与日期处理、不支持Bridge、依赖漂移。

最后一条是有真实网站读取的验证命令，当前可能因下面的BUG-002以非零退出；不能把非零退出忽略为整体通过。机器证据中的失败轮来自实际执行，不是故障模拟。
