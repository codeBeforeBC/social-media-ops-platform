## 数据关系及并发约束

| 对象 | 收口规则 | 后续实现/验证 |
|---|---|---|
| 通用 version | 代表乐观锁；不与revision_no、AssetVersion.version_no混用 | 更新事务检查expected_version；冲突返回最新版本 |
| Topic | 补parent_topic_id，默认每题只采纳一次 | TopicDecision接受唯一性，事务创建内容及Outbox；变体另建题 |
| Content | 补supersedes_content_id；与Publication账号一致 | 修订工作项不能循环或跨账号；原发布对象保持published |
| ContentRevision | 冻结后不可变；payload_hash由服务器生成 | 图文/视频转换新建版本；旧版保留，审核校验当前指针和哈希 |
| Publication | 初次revision_id不变，current_revision_id记录外部确认版本 | `(account_id,platform_note_id)`永久唯一；edited引用批准修订工作项；reposted新记录 |
| Campaign | 通用version用于编辑；campaign_version用于提醒计划 | 时间/规则/接收人/提醒规则改变时提升campaign_version；所有相关保存和Outbox同事务 |
| CalendarEvent | 普通事件持久化；开奖只由Campaign投影 | 禁止普通接口写draw；拖拽开奖落活动命令；多节点应用原子校验 |
| ReminderOccurrence | 唯一(campaign_id,campaign_version,rule_id) | 提醒发送事务锁活动并复查版本/状态，再写唯一通知；改期事务使用同一锁序 |
| Notification | channel为in_app，读/失效与业务完成分离 | 唯一(occurrence_id,recipient_id,channel)；改期已发通知superseded；停机合并补偿 |
| MetricObservation | 补aggregation_kind、source_definition和精确decimal传输 | 活跃confirmed逻辑键唯一；窗口/快照时间按来源粒度，空字段不造成重复漏洞 |
| MetricEvidence | 允许多个批次证明同一观察，active标记可撤销 | 同键同值不复制观察；撤销一个证据不破坏其他有效来源 |
| ObservationSupersession | 记录old/new/batch/reason链 | 同逻辑键确认与撤销序列化，先检查后续有效更正；不能盲恢复旧值 |
| Calculation | 补id、输入观察集合、公式/舍入版本、窗口/流量类型 | 数字只由程序算；Report事实引用calculation_id，撤销数据传播stale |
| IdempotencyRecord | 按workspace/actor/method/route/key识别，保存请求哈希/结果 | 并发唯一约束；相同键不同载荷409；不以30天缓存替代永久业务唯一性 |
| Job/Outbox | 输入版本、取消标记和租约在提交结果时复查 | 至少一次执行，结果幂等；不能自动将过期模型结果应用到新稿 |

跨工作区/跨账号约束除了API还需数据库复合外键或事务内归属校验。资产/文件历史不硬删除；成品归档是视图。建议以显式SQL实现部分唯一索引、锁和复杂约束，SQL迁移在S1/S2开始实际执行。

## 请求形状与接口扩展

`contracts/openapi.json`将06的组合方法展开到独立路径；补认证、任务重试、预览、资产版本/衍生关系和报告人工确认。Cookie认证、写操作CSRF、创建/关键命令幂等、PATCH版本字段已声明。

- ID采用UUID，发布平台ID保留字符串；内部角色映射admin/editor/reviewer/operator/viewer。
- 数值value采用精确十进制字符串，null必须有missing_reason；近似值统一is_approximate。
- ImportRow修改的指标载荷使用`metric: MetricInput`整体结构，包含target、metric_key、value、unit、window、observed_at等；避免更新一半口径。原始OCR值与人工更正分开保存。
- ContentRevision写入显式media_type；graphic要求pages且不接受shots，video要求shots且不接受pages。AssetUsage支持同页多个真实版本；页顺序/分镜时长用业务守卫继续检查。
- ReportPayload是AI生成结构，持久化后由服务端给行动分配稳定ID以支持accept-actions；模型不能自创数据库ID。
- response实体按05的逻辑模型建立扩展式对象，核心状态/数值/集合显式类型；不将所有字段设为必填。各模块实施时补关系详情视图与路由专用输出，变更须保持客户端和契约同版。

## 必须由业务服务检查的约束

JSON Schema能检查类型、枚举、必填和部分条件，不能代替以下检查：

1. 审核者权限、当前revision/哈希、成品可用和资产可用性。
2. 视频end>start、从0起的连续主镜头、终点与目标时长、片段范围。
3. 活动发布≤截止≤开奖，历史补录原因，人工开奖证据，以及对外规则变更触发内容修订。
4. 来源/资产ID属于输入允许集合且跨区不可读；外部URL域、IP和重定向校验。
5. 指标非负/净增可负、窗口和流量口径、分母、累计异常以及有效观察唯一性。
6. 文件真实格式、实际大小/哈希、原件与代理角色，以及预算并发占用。
7. 已读不改业务任务；通知产生与改期的竞争；导入撤销不覆盖后续更正。

这些在S1–S9测试，S0的21个合成Schema样例仅证明契约拒绝若干非法形状，不是上述功能测试。验证报告见 [contract-validation.json](../evidence/s0/contract-validation.json)。
