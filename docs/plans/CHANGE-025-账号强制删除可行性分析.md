# CHANGE-025 账号强制删除可行性分析

2026-10-29；Codex。本文件响应用户“关联仅警告，仍可强制删除账号及其选题、任务等”的分析请求。这里只提出方案，没有实现新删除行为或执行数据删除。实际状态仅见[开发进度](../tracking/开发进度.md)。目录 `/Users/junlong/projects/social-mdeida-ops-platform`，分支 `codex/s9-acceptance`，基线 `ad4edd7` 加既有未提交修改。

## 结论与规则变化

可行，也适合本地个人实例清理误填账号或试用数据。当前“有关联就拒绝”属于原业务规则，可以按用户新要求调整为：展示删除影响与不可恢复说明后，由用户点击“删除账号及关联数据”；普通账号私有记录不再作为阻止条件。仍沿用用户已明确的“不输入本地备注名称”交互。

“强制”表示允许清除该账号专属记录，不能扩大为其他账号、整个工作区或真实平台账号的清理权限。技术故障仍需如实失败或重试，不能为了看起来删成功而丢失剩余清理工作。

## 现有实现需要处理的约束

- [当前删除命令](../../apps/api/src/commands.ts)锁父账号并检查所有外键，但只覆盖空登记；账号的多层子记录、JSON快照、缓存、通知及私有对象未形成完整清理闭包。
- [选题迁移](../../packages/db/migrations/013-topics.sql)中证据/决策禁止普通删除；[指标历史](../../packages/db/migrations/028-metric-confirmation.sql)、[计算历史](../../packages/db/migrations/030-metric-calculations.sql)、[验证记录](../../packages/db/migrations/040-account-verification.sql)也有删除限制；[retired历史](../../packages/db/migrations/026-retire-cancelled-workflows.sql)含冻结数据。需要新增迁移建立受控账号清理通道，保留普通业务的历史保护，不直接改已应用旧SQL或全局禁用触发器。
- [Job底座](../../packages/domain/src/jobs.ts)有领取、租约、取消及结果提交。仅删任务行或设cancelled不足以证明外部处理已停止；必须阻止旧worker提交，处理已发出的模型/浏览器/解析器调用与可能生成的临时对象。
- [存储](../../packages/domain/src/storage.ts)提供对象删除和分片中止，但数据库事务不能回滚已经删除的对象；需要独立可靠清理清单及重试，不能把对象清单和待清理任务也随账号一起删掉。
- AI运行/用量、通用Job、通知等不全由account_id直接标识；有的对象可被多个业务引用。不能仅按表名或外键递归无差别删除，须明确归属和共享引用。

## 推荐清理边界

| 对象 | 建议处理 |
|---|---|
| 账号、账号成员关联、该账号验证与人工确认 | 强制删除范围内；清理确认外键和依赖后移除 |
| 选题、证据引用、采纳/拒绝决定、生成请求及账号专属快照 | 随账号清理；共享来源原文保留 |
| 已发布笔记本地登记、导入批次/行、指标、计算、复盘、策略、反馈及关联关系 | 如属于目标账号，纳入完整清理；删除本地登记不操作平台原笔记 |
| 专属任务、Outbox、由这些任务产生的通知/缓存/旧幂等响应 | 先停止/隔离，再清理；旧请求重放不能返回旧内容或重新建立账号 |
| 上传原件、预览、临时对象及未完成分片 | 无其他保留引用时中止上传并清理；持久化清单在账号移除后仍可执行 |
| 模型用量与已发生费用 | 不应因删除账号释放或重置已发生预算；建议保留不含提示词/账号身份的用量汇总 |
| 删除操作审计/回执 | 建议保留一条最小操作记录：时间、结果、数量、请求号，不保留已删业务正文 |
| 工作区/默认用户、AI配置及密钥、其他账号、共享来源连接/线索、浏览器档案与平台会话 | 保留；仅解除本账号自己的引用 |

新发现未知归属或跨账号引用时，应保留共享对象并说明处理结果，不能自动吞并其他账号数据。原目标此前只读查到的6个选题、1条AI生成、1条任务及1条事件应成为可清理对象，不再仅因这些记录存在就拒绝；实施时需重新预览，不能把之前的数量当当前数量或完整闭包。

## 推荐执行流程

1. **预览影响**：读取并分类统计该账号专属数据、文件及运行任务，明确共享对象/配置会保留。确认界面直接展示警告和“取消 / 删除账号及关联数据”，无需名称输入。确认时再次核对范围，避免预览后新增关联被悄悄扩大清理。
2. **建立独立删除操作**：确认后持久化操作ID，并将账号标记为deleting；删除期间不再允许新生成、导入、登记、验证或读取敏感下载。所有写入口、调度、任务提交和旧幂等响应必须服从该状态。删除操作及进度记录不能外键依赖即将移除的账号。
3. **隔离后台活动**：取消待执行任务、停止未派发事件，撤销运行任务的提交能力；向可取消的外部处理传递中止信号。不能中止的调用可能已发生费用，需允许其终止后做残留清理，不能重新把结果写回已删除账号。
4. **受控清理数据库**：冻结目标范围，按真实依赖关系清理叶子记录、快照/引用、专属任务与主账号，处理循环外键，使用事务保证数据库阶段一致。普通编辑仍受不可变约束，只有授权的账号清理路径允许移除对应历史；不得全局关闭外键或触发器。
5. **清理存储并完成回执**：数据库与文件不能宣称跨系统原子提交。通过独立清单幂等删除对象/中止分片，失败保留进度并重试。若账号已从日常列表隐藏但文件仍在清理，显示“关联文件清理中”，不能先宣称已彻底清除。完成后保留最小回执，防止旧请求/旧worker恢复数据。

数据少时前端可等待短时间完成；长期方案建议使用独立后台删除任务，页面展示“正在停止任务 / 清理记录 / 清理文件 / 已完成或失败”。用户操作仍只有一次明确确认，关闭页面不丢进度，重启后从同一操作继续。

## 恢复与测试建议

建议操作前保留可恢复备份，并明确删除后没有页面一键撤销，恢复依靠备份；备份保留周期与业务清理分开，不应默认把备份也删除。现有整实例备份会停止应用写入，不适合直接放入普通删除HTTP请求；可采用独立维护流程，或在账号冻结后实现受限账号级快照，具体方式需在实施方案中明确。若备份或清理失败，页面应给出真实状态和后续动作，而不是静默回到原列表。

实施至少验证：空账号；仅选题/任务；笔记/导入/指标/文件完整链；验证历史与retired数据；其他账号及共享来源保持；运行任务/晚到回写；并发创建与删除；重复点击/旧幂等键；服务重启；对象删除部分失败与重试；删除操作自身不被清理；实际用量预算不重置；失败提示在当前视野可见。

这项能力涉及数据生命周期、任务和存储，需要完整关联清单与配套迁移，不应通过简单移除409检查或把全部外键改为CASCADE实现。正式估时应在闭包及共享引用盘点后确定，本分析不虚报当前数据已全部覆盖。
